# Advanced / День 2 — Profiles: отчёт

Профили — файлы субагентов в корне репозитория (подхватываются автоматически в новых сессиях):
`.claude/agents/bug-fix.md`, `research.md`, `docs-sync.md` (третий, «усиление»).
Версии до доработки — `profiles-v1/`, после — в `.claude/agents/` (v2). Диффы результатов:
`bugfix.diff`, `docs-sync.diff`. Проект — копия сервиса (`week 8/day 2/`), исходное состояние перед
запусками сохранено вне репозитория для сравнения.

Запуск: каждому агенту дан один промпт «работай по профилю X (прочитай файл) + задача», без уточнений.
В текущей сессии новые определения агентов не подгружаются, поэтому исполнитель — general-purpose
агент, которому велено следовать файлу профиля (как и в day 1).

## Прогоны (первая попытка, v1)

### Research — «Какие эндпоинты сервиса не покрыты тестами?» → ✅ с первого раза
Ответ: 5 маршрутов; **`POST /publish` не покрыт ни одним тестом** (в `test_digest.py` он только в
docstring и в тексте `print`, вызывается `send_telegram` напрямую); `/generate` — частично (только
интеграционный тест с сетью и ключом, нет офлайн-проверок `last`/ошибок GitHub); `/stats` — полностью
(`mock.patch`); `/` и `/health` — в интеграционном тесте. Номера строк (`app.py:26,31,36,69,88`, `test_digest.py:53-57`,
`test_stats.py:28-39`) проверены вручную — верны. Файлы проекта не изменены (сравнением `cmp`). Находка сверх
вопроса: строка «/publish деградирует» в `test_digest.py` вводит в заблуждение.

### Bug Fix — «Нечисловой `last` в форме → HTML 500» → ✅ с первого раза
- Воспроизведение: `POST /generate` c `last="abc"` → 500 `text/html` (также `"1.5"`, `{"a":1}`, `[1]`).
- Причина: `app.py:49` — `int(data.get("last") or 15)` без `try/except (TypeError, ValueError)`; в `/stats` та же
  проверка уже была, в `/generate` — нет.
- Фикс (`bugfix.diff`): `try/except` → `{"error": "Параметр last должен быть числом."}`, 400 (текст и код как в `/stats`).
- Регрессионный тест в `test_stats.py` на 4 плохих значения; на старом коде падает (`AssertionError: abc`), на новом проходит.
- Проверено мной независимо: диф минимален, `test_stats.py` ✅, `test_digest.py` ✅ (вызывает реальные GitHub/DeepSeek —
  в окружении есть `DEEPSEEK_API_KEY`), ruff ✅, три плохих значения → JSON 400.

## Что сильнее всего влияло на результат

1. **Жёсткий порядок шагов** (воспроизвести → причина → baseline → фикс → тест → проверка) — Bug Fix
   сам доказал, что тест падает на старом коде.
2. **Технический запрет вместо словесного**: у Research нет Edit/Write — «не менять код» гарантировано, а не просто написано.
3. **Обязательный формат ответа** с разделом «Что не проверено» — исполнители честно перечисляли пробелы
   (ключ/сеть, непроверенные тесты), что позволило их быстро перепроверить.
4. **Требование ссылок `файл:строка`** — ответ Research проверяется за минуту.
5. **Окружение в самом профиле** — без него исполнитель гадал про venv/ruff/git.
