# День 7 — свой датасет: классификация git-коммита в JSON

**Итог:** на eval из 104 коммитов дообученная модель даёт **72,1 % accuracy** против **33,7 %** у той же базы
с проработанным промптом (и 0 % без инструкций); формат ответа — 100 % строгий JSON.

## Задача и что считается верным ответом

По тексту git-коммита (`subject` + `body`, без префикса) вернуть **ровно один JSON** `{"type": "<тип>"}`,
`<тип>` ∈ `feat, fix, docs, refactor, test, chore, perf, ci`. Верно = ответ — валидный JSON с единственным
ключом `type`, значение совпадает с эталоном (метка из префикса Conventional Commits оригинального коммита).

Отклонение от первоначального плана: поле `breaking` убрано — в собранных данных его всего 24 положительных
примера из 4003 (0,6 %), метрика была бы шумной, учить не на чем. Также в eval нет «грязных» входов
(merge-коммиты, off-topic): у них нет однозначной эталонной метки.

## Данные

| Шаг | Результат |
|---|---|
| Источник | последние ≤100 коммитов 48 публичных репозиториев с Conventional Commits (`github_repo.get_commits`, только чтение) |
| Разметка | метка = префикс заголовка (`fix(api)!: …` → `fix`), префикс из входа удалён → 4003 размеченных коммита |
| Дедупликация | точные дубли по нормализованному заголовку + почти-дубли (Жаккар слов ≥ 0,8) → 3415 |
| Eval | 8 репозиториев целиком (vue/core, nest, python-storage, electron, TanStack/query, deno, commitizen, unocss), по ≤13 на класс → **104** |
| Train/valid | остальные 40 репозиториев, ≤250 на класс; valid 8 % → **train 1354 / valid 118** |
| Формат | `messages` (как в дне 6): user = `Commit message:\n<subject>\n\n<body>`, assistant = `{"type": "fix"}` (компактный JSON) |

Баланс train: chore 235, fix 236, feat 224, docs 224, test 129, perf 116, refactor 103, ci 87
(без ограничения доминировали `fix` 1489 и `chore` 1104 из 4003). Eval сбалансирован — по 13 на класс.
`test_dataset.py` проверяет формат, отсутствие пересечений eval с train по репозиториям и по тексту, баланс.

### Просмотр 30 случайных примеров train (`data/review_sample.jsonl`)

Эталонные метки — следствие соглашений авторов, а не ошибки парсера. Из 30 примеров ~5 спорных:
`add timeout parameter to to_dataframe…` помечен `fix` (по смыслу `feat`), `factor object type opening brace`
— `perf` (похоже на `refactor`), `add new batch.#is_skipped method` — `chore`, `add rich admonition title
dogfooding` — `test`. Вывод: часть меток шумная (~15 % по выборке), **потолок accuracy заметно ниже 100 %**;
руками метки не правились, чтобы датасет оставался воспроизводимым скриптами.

### Утечка метки через тело коммита (найдена при разборе)

В теле некоторых squash-коммитов (googleapis, renovate) дублируется исходный заголовок с префиксом
(`refactor: move system tests…`). Затронуто: train 10, valid 1, eval **9 из 104**. Влияние на вывод проверено:
на 95 eval-примерах без такой утечки tuned = **71,6 %**, base_prompt = **30,5 %** — выводы не меняются.
Датасет в этом прогоне не пересобирался.

## Базовая линия (до тюнинга), Qwen2.5-1.5B-Instruct, eval 104

| Режим | Accuracy | Строгий формат | Macro-F1 |
|---|---|---|---|
| base_plain (вход без инструкций) | 0,0 % | 0,0 % | 0,000 |
| base_prompt (правила + определения типов + 8 примеров, «только JSON») | 33,7 % | 98,1 % | 0,278 |
| **tuned (LoRA, вход как в base_plain)** | **72,1 %** | **100 %** | **0,725** |

`base_plain` = 0 %: без инструкций модель пишет рассуждения («The commit message indicates…»), а не JSON.
`base_prompt`: два нестрогих ответа (JSON в ```-блоке и выдуманный тип `bug-fix`).

### Что изменилось и где тюн хуже

- **Лучше на 47 примерах, хуже на 7** относительно base_prompt. База «сваливала» всё в `feat` (refactor→feat 9,
  perf→feat 8, docs→feat 7) и в `chore`; тюн научился различать редкие классы.
- **Регрессии (7):** `chore` стал хуже классифицироваться (0,77 → 0,54): `update deps version for test` → `test`,
  `replace semver with verkit in release script` → `ci`, `drop az, capacity_builder…` → `perf`, `skip failing
  samples…` → `test`; ещё `fix`→`docs` (nest, «map unsupported multipart content types to 415»), `feat`→`test`
  (benchmarks), `refactor`→`test`. Слова-триггеры (`test`, `release`, `drop`) перетягивают на «тематический» класс.
- **Самые частые ошибки тюна:** `ci → chore` (6), `chore → test` (4). Граница ci/chore/test размыта у самих авторов.
- По репозиториям (малые выборки, шум): electron 0,94, deno 0,81, TanStack/query 0,79, … nestjs 0,50
  (8 примеров), commitizen 0,45 (11) — репозитории со своей спецификой формулировок.

## Обучение

| Параметр | Значение |
|---|---|
| Железо | сервер 192.168.1.4, AMD Radeon 8060S (Strix Halo, gfx1151), ROCm 7.13, PyTorch 2.11.0+rocm7.13.0 |
| Модель / метод | `Qwen/Qwen2.5-1.5B-Instruct`, LoRA bf16 (r=16, alpha=32, dropout 0,05, все linear-слои) |
| Обучаемых параметров | 18,46 млн (1,18 %), адаптер `adapters/` ≈ 70 МБ |
| lr / scheduler | 2e-4, cosine, warmup 15 шагов |
| Эпохи / batch / шаги | 3 / 16 / 255 |
| max_len / seed | 384 / 42 |
| **Время обучения** | **677 с ≈ 11,3 мин** |
| Пик памяти (allocated) | 31,8 ГБ (общая память с CPU, без gradient checkpointing) |

Loss (train / eval): шаг 25 — 0,269 / 0,208; 50 — 0,165 / 0,166; 100 — 0,106 / 0,125; **150 — 0,091 / 0,114 (минимум eval)**;
200 — 0,038 / 0,127; 255 — 0,019 / 0,134. После шага ~150 train падает, eval растёт — **переобучение на 3-й эпохе**;
адаптер сохранён с конца обучения. Достаточно было ~2 эпох (ранняя остановка по eval loss).

## Выводы

- Узкая задача с проверяемым ответом: тюн на 1354 примерах (11 минут) **вдвое превзошёл** проработанный промпт
  по accuracy (72,1 vs 33,7 %) и удвоил+ macro-F1 (0,725 vs 0,278), при этом убрал нестрогий формат (98,1 → 100 %)
  и не требует длинного промпта (входной контекст короче в разы).
- Основной выигрыш — на редких классах (`perf`, `docs`, `test`, `refactor`); `chore` и `ci` остаются слабым местом.
- Улучшения на следующий прогон: ранняя остановка (2 эпохи), подмешать больше `ci`/`chore`, убрать утечку из тела
  коммита, ручная чистка спорных меток.

## Что НЕ проверено

- Один прогон и один seed; доверительные интервалы не считались (104 примера — разница 72 vs 34 % значима,
  но различия между классами на 13 примерах — нет).
- Метки датасета — автоматические (префикс), шум ~15 % оценён по выборке из 30, а не на всём датасете.
- Утечка метки через тело коммита не исправлена, влияние оценено только на eval.
- Только один баз-промпт (8 примеров, написаны вручную); другие промпты/few-shot из train не пробовались.
- Не проверены другие размеры модели и сравнение с большой моделью (API) как верхней границей.
