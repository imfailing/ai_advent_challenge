# День 7 — свой датасет: классификация git-коммита в JSON

**Итог (v2, финальный прогон):** на eval из 104 коммитов дообученная модель даёт **69,2 % accuracy**
против **26,9 %** у той же базы с проработанным промптом (0 % без инструкций), macro-F1 0,690 против 0,161,
формат ответа — 100 % строгий JSON.

## Задача и что считается верным ответом

По тексту git-коммита (`subject` + `body`, без префикса) вернуть **ровно один JSON** `{"type": "<тип>"}`,
`<тип>` ∈ `feat, fix, docs, refactor, test, chore, perf, ci`. Верно = ответ — валидный JSON с единственным
ключом `type`, значение совпадает с эталоном (метка из префикса Conventional Commits оригинального коммита).

Отклонения от первоначального плана: поле `breaking` убрано — в собранных данных всего 24 положительных
примера из 4003 (0,6 %), метрика была бы шумной; в eval нет «грязных» входов (merge-коммиты, off-topic) —
у них нет однозначной эталонной метки.

### Просмотр случайных примеров

Из 60 просмотренных примеров train 10 (≈17 %) имели неверную или бессодержательную метку
(`chore: add blog post` — по смыслу `docs`; `fix: update dependency preact` — `chore`; `chore: simplify`,
`docs: improve` — без сигнала; и т. п.). В первой выборке из 30 было ~5 спорных (~15 %). Найденные примеры
удалены, остальные метки **не правились** — шум остаётся (оценка 15–17 % до чистки, после — неизвестна, т. к. просмотрено
лишь 90 из 3401 примеров), потолок accuracy ниже 100 %.

### Утечка метки через тело коммита (найдена в первом прогоне и устранена)

В теле squash-коммитов (googleapis, renovate, …) дублируется исходный заголовок с префиксом
(`refactor: move system tests…`, `* feat(presets): …`). В v1 это затронуло 9 из 104 eval-примеров и
10 из 1354 train. В v2 убрано полностью (проверка в тесте). Эффект виден в базе с промптом: она упала с 33,7 % до 26,9 %
— часть её точности давала утечка. Тюн в v2 оценён честно.

## Базовая линия (до тюнинга), Qwen2.5-1.5B-Instruct, eval 104 (v2)

| Режим | Accuracy | Строгий формат | Macro-F1 |
|---|---|---|---|
| base_plain (вход без инструкций) | 0,0 % | 0,0 % | 0,000 |
| base_prompt (правила + определения типов + 8 примеров, «только JSON») | 26,9 % | 98,1 % | 0,161 |
| **tuned (LoRA, вход как в base_plain)** | **69,2 %** | **100 %** | **0,690** |

`base_plain` = 0 %: без инструкций модель пишет рассуждения («The commit message indicates…»), а не JSON.
`base_prompt`: два нестрогих ответа (JSON в ```-блоке и выдуманный тип `bug-fix`).

### Что изменилось и где тюн хуже

- **Лучше на 52 примерах, хуже на 8** относительно base_prompt. База «сваливает» всё в `feat` и `chore`
  (ci→chore 12, refactor→feat 11, docs→feat 8, perf→feat 8); тюн научился различать редкие классы.
- **Регрессии (8):** `feat` и `chore` стали хуже, чем у базы: `feat → fix` (3, python-storage и electron:
  `expose finalized_time…`, `support chrome.storage.sync…`), `feat → test` (benchmarks), `chore → ci` (3:
  `replace semver with verkit in release script`, `librarian generate pull request`, `skip failing samples…`),
  `chore → perf` (`drop az, capacity_builder…`). Класс `feat` потерял точность (0,85 → 0,62): тюн реже выбирает
  «умолчание» базы, но ошибается соседними классами.
- **Самые частые ошибки тюна:** `ci → chore` (4), `refactor → feat` (4), `feat → fix` (3), `fix → perf` (3), `chore → ci` (3).
- По репозиториям (малые выборки): unocss 0,83, electron 0,82, TanStack/query 0,75, deno 0,75, commitizen 0,64,
  nestjs 0,62 (8 примеров) и **googleapis/python-storage 0,31** (13) — у этого репо метки `feat` на «expose …»
  и `chore` на служебные библиотечные коммиты; это шум эталона и особенность репо, а не только ошибка модели.

## Выводы

- Узкая задача с проверяемым ответом: тюн на 981 примере (5 минут) **в 2,6 раза превзошёл** проработанный промпт
  по accuracy (69,2 vs 26,9 %) и в 4,3 раза по macro-F1 (0,690 vs 0,161); формат 100 % строгий JSON без длинного промпта.
- Выигрыш — на редких классах (`perf`, `docs`, `test`, `ci`, `refactor` были почти нулевые у базы). Цена: `feat` и `chore`
  у тюна хуже, чем у базы, которая просто выбирала их по умолчанию.
- Слабое место — шум эталона и соседние классы (`ci`/`chore`, `refactor`/`feat`, `feat`/`fix`).
- Дальше: расширить данные для `ci`/`refactor`, прогнать несколько seed, почистить метки по всем данным
  (например, LLM-судьёй с ручной проверкой спорных), проверить другой размер модели.

## Что НЕ проверено

- Один прогон и один seed на версию; доверительные интервалы не считались (разница 69 vs 27 % значима,
  различия между классами на 13 примерах и между v1/v2 — нет).
- Метки остались автоматическими; шум оценён только по 90 просмотренным примерам, остальные ~3300 не проверялись.
- Один баз-промпт (8 примеров, написаны вручную); другие промпты и few-shot из train не пробовались.
- Очистка тела убирает строки с префиксом по регулярному выражению; другие формы утечки могли остаться.
- Нет сравнения с большой моделью (API) как верхней границей и с другими размерами Qwen.
