# Как выкатывать новую версию модели

Сервис не перезапускается: он читает `registry/state.json` на каждый запрос, активная модель меняется одним вызовом.

## Где что лежит
| Что | Где |
|---|---|
| Адаптер LoRA (исходник версии, ~70 МБ) | сервер `llm-server`, `week 9/day N/adapters/` (в git нет) |
| Слитая HF-модель и GGUF (f16, Q8_0, Q4_K_M) | сервер, `~/models/<версия>-hf`, `~/models/<версия>-<квант>.gguf` (в git нет) |
| Каталог версий, режим промпта, порт, **sha256** файла | `registry/models.json` (в git) |
| Какая версия активна и стек предыдущих | `registry/state.json` (локально у сервиса, в git нет) |
| Результаты проверок перед выкаткой | `registry/verified.json` (локально у сервиса) |
| Запущенные модели | `llama-server` на сервере, порты 8081–8083, только 127.0.0.1; к ним — SSH-туннель |

## Выкатка новой версии (`tuned-v2`)
1. **Слить и сконвертировать** (на сервере): `python scripts/merge_adapter.py ~/models/tuned-v2-hf <адаптер>`, затем
   `convert_hf_to_gguf.py … --outtype f16` и `llama-quantize … Q8_0`. Брать Q8_0: она не теряет точность относительно f16,
   Q4_K_M теряла 4,8 п.п. (см. REPORT.md). Любой квант нужно измерить сам.
2. **Замерить:** `python scripts/bench_gguf.py <имя> ~/models/tuned-v2-Q8_0.gguf plain` — размер, память, загрузка, скорость, качество.
3. **Зарегистрировать:** добавить запись в `registry/models.json` (свободный порт, `mode`, `gguf`, `sha256sum` файла),
   запустить новый `llama-server` (`scripts/serve.sh`, порт новой версии), открыть туннель.
4. **Проверить до выкатки:** `python scripts/verify_model.py tuned-v2 --baseline tuned-v1`. Критерии: точность ≥ 0,60 на
   `data/eval.jsonl` (104 коммита, не входят в обучение), доля строго валидного JSON ≥ 0,95 и точность не ниже
   активной версии больше чем на 2 п.п. Код выхода 0 — можно, 1 — нельзя. Результат записывается в `registry/verified.json`.
5. **Включить:** `POST /models/activate {"id": "tuned-v2"}`. Сервис откажет, если проверка не пройдена или сервер модели
   не отвечает (`force: true` обходит это — только для разбора аварий).
6. **Канарейка:** прежде чем оставить, прогнать `scripts/compare_live.py` и посмотреть распределение типов и задержку
   на живых репозиториях; для разового сравнения на другой версии использовать параметр `model` у `/classify`
   (он не меняет активную).

## Откат
```bash
curl -X POST localhost:5012/models/rollback        # вернуть предыдущую версию из стека (до 10 шагов)
curl -X POST localhost:5012/models/activate -H 'Content-Type: application/json' -d '{"id":"deepseek-v4-flash"}'  # или явно
```
Откат занимает миллисекунды (проверено: 2 мс на `rollback`, 11 мс на `activate`), перезапуск не нужен. Предыдущая
версия остаётся запущенной и в реестре, поэтому откат безопасен, пока её `llama-server` жив. Прежний облачный
вариант (`deepseek-v4-flash`) включается без проверки и без локальной модели — это запасной выход, если упал сервер.
Если версию нужно убрать совсем: откатиться, остановить её `llama-server`, удалить запись из `models.json`,
файлы с сервера удалять не сразу.

## Что проверять после выкатки
`GET /models` (активная версия, `online`), доля `unknown` в `by_type` ответа `/classify` (рост = модель перестала
отвечать JSON), средняя задержка `avg_seconds`.

## Ограничения процедуры
Проверка на фиксированных 104 коммитах не заменяет наблюдение за живым потоком. Признанный порог 0,60 мягкий и
подобран под нынешнюю точность ≈ 0,7. `registry/state.json` локален: при нескольких инстансах сервиса нужен общий
файл или БД. Целостность GGUF (`sha256`) записана в реестре, но сервис её сам не сверяет.
